# Own the local box, integrate the rest

> **Status update (2026-10-08).** The three correctness defects this report calls "fix first" have been **fixed**, along with three more found while fixing them. Each has a regression test in `tests/integration/test_failure_semantics.py`. Bugs 1 and 3 were reproduced on the original code and re-checked live against Foundry Local CLI 0.10.3. Bug 2 is verified by unit tests only. See [the updated defects section](#the-three-defects-are-fixed) and `CHANGELOG.md`.
>
> One correction to the research: on Foundry Local CLI 0.10.3, `/openai/status` and `/openai/loadedmodels` return **404**, so recommendations that rely on them (ranks 10 and 11 and roadmap Phase 3 below) need a CLI-0.10 adapter (`foundry status --output json`, `/v1/models`) instead. Live measurements, including that 0.10.3 still processes requests one at a time on a CUDA GPU, are in `docs/ARCHITECTURE.md` §19. The rest of the report is unchanged from the original survey.

No gateway or local proxy surveyed does what KVStream does: KV-token admission against a measured budget, for a single local runtime that publishes no metrics, with predictive shedding and Retry-After. Every multi-provider gateway (agentgateway, Agent Router, LiteLLM, Portkey, Bifrost, Helicone, TensorZero, LLM Gateway, Kong, APISIX, Azure APIM, Cloudflare) charges token limits against quotas *after* the response and treats backends as remote, elastic APIs. The local servers (Ollama, llama.cpp, LM Studio) queue with little or no overload signalling. Foundry Local has no queue, no batching and no metrics endpoint at all. That gap is KVStream's product. For **multi-call agentic workflows on one CPU/GPU/NPU machine**, three changes matter most. First, fix three correctness defects that undercut its differentiators: 4xx responses trip the circuit breaker; a cancelled coalescing leader strands its followers; streamed followers get a truncated stream that looks complete (*all three now fixed; see the status note above*). Second, move from per-request FIFO to **session-aware scheduling**, so an admitted agent finishes before new ones start. Third, lean on Foundry-specific surfaces (exact token counting, model load/TTL control, dynamic-port status, a process-memory watchdog) that no general-purpose gateway will ever build. Everything else (auth, tenancy, guardrails, MCP/A2A, cloud failover) already exists in mature gateways that can sit in front of KVStream. KVStream should publish reference configurations for them, not reimplement them. The landscape also shifted in 2026: Envoy AI Gateway was renamed Agent Router and joined the Agentic AI Foundation, agentgateway joined too, Helicone went into maintenance mode, LiteLLM suffered a PyPI compromise, Portkey was acquired, and Foundry Local was re-architected as an in-process SDK. Several of KVStream's integration assumptions need revisiting as a result.

*How to read this report.* Claims tagged **[S]** are sourced (citation inline). **[I]** marks the author's inference or design judgement. **[K]** marks findings from review of the KVStream codebase (`src/kvstream`), which were spot-checked against the source for this report. KVStream is scoped to **Microsoft Foundry Local only**. Multi-provider gateways appear here as sources of patterns and as things KVStream can sit behind, never as features to build.

## Every surveyed gateway protects quotas; none protects a single machine's capacity

Products in this space split into four layers, and each solves a different problem. **Agent-native and Envoy-based gateways** (agentgateway, Agent Router, kgateway/Solo) are data planes for LLM, MCP and A2A traffic. **Application-layer multi-provider gateways** (LiteLLM, Portkey, Bifrost, Helicone, TensorZero, LLM Gateway, OpenRouter) normalise providers and add budgets, fallbacks and observability. **API-vendor gateways** (Kong, APISIX, Azure APIM, Cloudflare) add AI plugins to existing API management. **Local inference servers and local proxies** (Ollama, llama.cpp, LM Studio, LocalAI, Olla, llama-swap) run or front models on one box. Two further categories fall outside KVStream's lane: MCP gateways (Docker MCP Gateway, IBM ContextForge, Microsoft MCP Gateway) federate *tools*, not inference, and the vLLM Semantic Router picks *models*.

The decisive pattern is how token limits behave. Azure APIM states outright that "concurrent or near-concurrent requests can temporarily exceed the configured token limit". Unless `estimate-prompt-tokens` is on, prompts reach the backend even after the limit is exceeded, and only later requests get blocked ([MS Learn llm-token-limit](https://learn.microsoft.com/en-us/azure/api-management/llm-token-limit-policy)). Kong's cost "is only reflected during the next request" ([Kong docs](https://developer.konghq.com/plugins/ai-rate-limiting-advanced/)). APISIX reads tokens from the response ([APISIX docs](https://apisix.apache.org/docs/apisix/plugins/ai-rate-limiting/)). agentgateway charges actual usage at response time and only estimates up front when `tokenize: true` ([agentgateway rate limits](https://agentgateway.dev/docs/standalone/latest/configuration/resiliency/rate-limits/)). Agent Router rejects with 429 once *accumulated* usage is over the limit ([usage-based rate limiting](https://aigateway.envoyproxy.io/docs/capabilities/traffic/usage-based-ratelimiting)). Cloudflare does not limit tokens at all; it counts requests and caps spend separately ([Cloudflare rate limiting](https://developers.cloudflare.com/ai-gateway/features/rate-limiting/)). **[S]** These vendors accept overshoot because they protect billing. On a single box, overshoot means KV exhaustion, swapping or a stall. KVStream's reserve-prompt-plus-max-output-then-settle model is the correct design for that goal, and the research found no vendor documenting it **[I]**.

Capacity measurement is equally absent. None of the application-layer gateways measures local KV or tokens/s, and none adapts concurrency. Their controls are static operator numbers such as LiteLLM's `rpm`/`tpm`/`max_parallel_requests` ([LiteLLM routing](https://docs.litellm.ai/docs/routing)) and Bifrost's `concurrency`/`buffer_size` ([Bifrost provider config](https://docs.getbifrost.ai/quickstart/gateway/provider-configuration)). Latency-aware schemes (Helicone PeakEWMA, OpenRouter rolling percentiles) choose *between* backends rather than sizing admission to one ([Helicone](https://github.com/Helicone/ai-gateway); [OpenRouter](https://openrouter.ai/docs/features/provider-routing)) **[S]**. The only capacity-aware routing in the survey is the Gateway API Inference Extension. Its endpoint picker scrapes KV utilisation and queue length from vLLM-class servers ([CNCF deep dive](https://cncf.io/blog/2025/04/21/deep-dive-into-the-gateway-api-inference-extension)), filters by request criticality (Critical vs Sheddable) ([kgateway blog](https://kgateway.dev/blog/deep-dive-inference-extensions)), and sheds when queue depth or KV utilisation pass safety limits ([GKE docs](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-gke-inference-gateway)) **[S]**. It is a Kubernetes multi-replica router that depends on engine metrics. Foundry Local exposes none, and its REST reference documents no metrics, health or queue endpoint ([Foundry Local REST reference](https://learn.microsoft.com/en-us/azure/foundry-local/reference/reference-rest)) **[S]**.

## Five capabilities make KVStream different, and three bugs undercut them (now fixed)

### What is genuinely differentiated

**Pre-admission token reservation.** KVStream reserves prompt plus max output at admission and settles to actual usage afterwards. Vendors document only post-hoc settlement or prompt-only estimates (sources above) **[S/I]**.

**A measured budget for a backend that reports nothing.** Foundry Local "isn't designed as a server inference stack" and lacks queuing or continuous batching ([Foundry-Local README](https://raw.githubusercontent.com/microsoft/Foundry-Local/main/README.md)). KVStream's calibration sweep and seconds-per-token drift monitor are the only saturation signal available for it **[S/K]**.

**Predictive shedding with Retry-After.** The nearest analogues are Ollama's 512-deep queue that eventually returns 503, with no Retry-After documented ([Ollama FAQ](https://raw.githubusercontent.com/ollama/ollama/main/docs/faq.mdx)), and Bifrost's drop-when-full buffer ([Bifrost config](https://docs.getbifrost.ai/quickstart/gateway/provider-configuration)) **[S]**. Refusing on arrival with a measured wait estimate (`app.py`, the `AdmissionTooSlow` path) is materially better for agents than letting up to 512 requests wait behind one slot **[K/I]**.

**A real-generation readiness probe.** LiteLLM is the only other product found that runs real generations for health. It deliberately keeps them off `/health/readiness` and caches the results every 300 s because generations cost money ([LiteLLM health](https://docs.litellm.ai/docs/proxy/health)). Local tokens are free, so KVStream can probe more often **[S/I]**.

**Streaming request coalescing.** No surveyed gateway documents fanning one upstream stream out to N clients. None of the gateway docs reviewed (agentgateway, LiteLLM, Bifrost, TensorZero, Portkey, Kong, APISIX, APIM, Cloudflare) lists request coalescing **[S, absence-of-evidence from the docs cited above]**. Add to this **Foundry-specific lifecycle handling**: no gateway's provider list includes Foundry Local, and all reach it only as a generic OpenAI-compatible endpoint ([Bifrost config](https://docs.getbifrost.ai/quickstart/gateway/provider-configuration); [agentgateway providers](https://agentgateway.dev/docs/standalone/latest/llm/providers/)) **[S]**.

The steelman against this niche is real. Olla already ships health checks, circuit breakers, rate limiting and KV-cache-aware affinity in under 50 MB of Go ([Olla](https://github.com/thushan/olla)). If ORT GenAI's new continuous-batching engine reaches Foundry's server, "Foundry serialises requests" stops being true (see the risks section). KVStream's defensible core is therefore *measured capacity plus overload semantics plus Foundry lifecycle*, not any single feature **[I]**.

### The three defects are fixed

*Updated 2026-10-08.* The survey found three defects that contradicted the product's own guarantees **[K]**. All three are fixed, each with a regression test in `tests/integration/test_failure_semantics.py`. Line numbers below refer to the code as it was reviewed. The fixed code no longer matches them.

| # | Defect as found | Fix | Verification |
|---|---|---|---|
| 1 | **Client errors opened the circuit breaker for everyone.** `backend/foundry.py` raised any upstream status ≥400 on chat as `FoundryError` (streaming ~304–312, non-streaming ~359–363). `app.py` mapped it to **502** (~1164) and recorded a backend failure (~458, ~591–600). A wrong model alias, the README's most common first-run failure, returned 502, and five of them opened the breaker (`failure_threshold = 5`), contradicting `backend/health.py` ~79–83. | 4xx is raised as `FoundryClientError`, which carries the backend's status and body. It reaches the client unchanged and is never recorded against the breaker. The model alias is checked at startup against `/v1/models`, not the `/openai/*` endpoints suggested originally, which return 404 on CLI 0.10.3. | Reproduced on the original code: seven bad requests gave five 502s, then 503s for everyone. Live on Foundry 0.10.3 after the fix: 7 of 7 returned 400, breaker closed. |
| 2 | **A cancelled coalescing leader stranded its followers.** `cache/coalescer.py` `Coalescer.run` caught only `Exception` (~59). `asyncio.CancelledError` is a `BaseException`, so a cancelled leader never resolved the shared future, and followers waited until their own timeouts. | A cancelled leader resolves the future with a hand-over signal, and a waiting follower becomes the new leader. Followers wait through `asyncio.shield`, so one follower's cancellation can no longer cancel the result the others share. | Unit tests. Not exercised live, because that needs a client disconnect that cancels the request handler. |
| 3 | **Streamed followers received a truncated stream that looked complete.** The `finally` block of `handle_streaming`'s `body()` generator in `app.py` (~660–665) always published `data: [DONE]`, even when the leader's client had disconnected mid-generation. Root cause: the upstream generation's lifetime was tied to the leader's HTTP connection. | Applied the structural fix proposed here. The gateway owns each generation as an `asyncio.Task` (`_run_stream`) publishing into the broadcast, and every client, the leader included, is a subscriber. The upstream call is cancelled when the last subscriber leaves. `[DONE]` is sent only when the upstream stream ends normally; an error or cancellation sends an SSE error frame instead. | Reproduced on the original code: the follower got 1 chunk plus `[DONE]`, and the leader's disconnect also raised `RuntimeError: async generator ignored GeneratorExit`. Live after the fix: the follower received all 113 frames ending in `[DONE]`, and abandoning a 900-token stream released its reservation immediately. |

**One deliberate deviation from the proposed fix.** This report suggested sending `[DONE]` "only on a real `finish_reason`". The fix sends it whenever Foundry ends the stream normally. Requiring a `finish_reason` would turn every response from a backend that omits it into an error. Abnormal endings never get `[DONE]`, which is the guarantee that matters to a client parsing tool-call JSON **[I]**.

**Three further defects were found while fixing these, and also fixed:**

* **A half-open breaker trial could wedge the breaker.** A trial that never reached a verdict (refused by admission, answered with a 4xx, or cancelled) left the breaker half-open, refusing every request indefinitely. Trials are now always released, with a timeout as a safety net.
* **One wrong alias switched off usage reporting for the whole process.** A 400 on a request carrying `stream_options` was read as "the backend rejects `stream_options`". It is now treated as rejected only if the retry without it succeeds.
* **Foundry 0.10.3 answers a streamed request for an unloaded model with `200 text/event-stream` and a dropped connection.** That looked like a crash, so it still counted against the breaker after fix 1. Streamed requests are now checked against `/v1/models` before dispatch and refused with 400 `model_not_found`. The check ignores a `:N` version suffix and fails open if the list is unavailable. Found live; 7 of 7 such requests returned 400 with the breaker untouched.

The underlying principle still stands: these bugs sat inside the differentiators (breaker semantics, coalescing, streaming), so they had to land before any new feature. Google SRE's advice to propagate cancellation "so abandoned work stops" is what fix 3 implements ([Google SRE: Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)) **[S]**.

## Agent workloads reward session-aware ordering more than raw throughput

Agentic programs suffer "long cumulative wait times, primarily due to head-of-line blocking at both the individual LLM request and the program" ([Autellix](https://arxiv.org/abs/2502.13965)). Per-call FIFO creates exactly this: turn N of an agent that has already done most of its work queues behind turn 1 of every newcomer. Agent traffic is also **prefill-heavy with short decodes**. Autellix's BFCL ReAct trace averages 10.75 calls per program with 735-token prefill and 34-token decode ([Autellix html](https://arxiv.org/html/2502.13965)). Continuum's SWE-bench traces average 10.9 turns and about 70K tokens per program, and tool latency is long-tailed: the slowest 10% of tool calls cause 52.5–94.1% of delay ([Continuum](https://arxiv.org/html/2511.02230v2)) **[S]**.

The research separates scheduling ideas that need only request visibility from those that need engine control. A black-box proxy can apply Autellix's PLAS priority (programs with less attained service go first), its anti-starvation β-promotion, Continuum's **program-level FCFS** (rank a call by its *program's* arrival time), VTC token fairness and SJF via learning-to-rank. Preemption, KV pinning and swapping, and live migration all require the engine ([Autellix](https://arxiv.org/html/2502.13965); [Continuum](https://arxiv.org/html/2511.02230v2); [VTC](https://arxiv.org/abs/2401.00588); [LTR-SJF](https://arxiv.org/abs/2408.15792); [FastServe](https://arxiv.org/abs/2305.05920); [Llumnix](https://arxiv.org/abs/2406.03243)) **[S]**. The reported gains are large: Autellix shows 4–15x program throughput over vLLM, and Continuum 1.12–3.66x lower delay. Both were measured on batching GPU engines, partly through engine features. On a serialising backend, throughput will not move. The win is mean program completion time, because the queue is where all the waiting happens **[I]**. No paper evaluates program-level scheduling at a pure black-box proxy, so KVStream must measure the gain itself.

Overload control needs the same session lens. Google SRE's criticality tiers (CRITICAL_PLUS through SHEDDABLE), its 10% retry budgets, deadline propagation and "small queues, reject early" guidance ([SRE Handling Overload](https://sre.google/sre-book/handling-overload/); [SRE Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)) map naturally onto agents. An admitted session is critical, because shedding it wastes every prior turn. A new session is sheddable **[I]**. Retries should happen at exactly one layer ([AWS Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)). KVStream should keep not retrying internally and should give clients a drain-derived, jittered `Retry-After` instead ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#field.retry-after)) **[S/I]**.

Adaptive concurrency needs care. Netflix Vegas/Gradient2 and Envoy's gradient controller infer congestion from latency inflation over minRTT ([Netflix concurrency-limits](https://github.com/Netflix/concurrency-limits); [Envoy adaptive concurrency](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter)). They would misread a 4K-token completion as congestion. Envoy also warns of "a noticeable increase in request 503s" during its minRTT re-measurement windows **[S]**. No primary source normalises the gradient by tokens. The natural KVStream adaptation is to feed the controller seconds-per-token from `admission/drift.py`: gradient = baseline_spt·(1+B)/recent_spt, seeded and clamped by calibration, with the baseline refreshed opportunistically when the queue is idle. The goal is to track the long-session slowdown, not to raise concurrency on a serialising runtime **[I]**.

Two structural notes **[I]**. First, ranks 2, 3, 4, 14 and 15 are all the *same* change: replace the single FIFO in `admission/capacity.py` with a pluggable `QueuePolicy` (class → session → program-arrival → SJF/aging), keeping reserve-then-settle and predictive shedding untouched. Build that seam once. Second, the ~1,350-line `Gateway` class in `app.py` should be split into explicit pipeline stages (classify → cost → cache/coalesce → admit → dispatch-task → stream/settle → metrics) *before* layering on sessions and gateway-owned tasks. Defect 3 is a symptom of streaming, coalescing and accounting being interleaved in one generator.

## Sit behind agentgateway or APIM, and keep MCP upstream

The integration answer is consistent across the notes. Every capability KVStream lacks (auth, TLS, RBAC, per-key token budgets, guardrails, OTel, MCP/A2A federation) is mature in gateways that can target `http://127.0.0.1:<kvstream-port>` as a custom OpenAI-compatible provider. agentgateway supports exactly this through a `custom` provider with `formats: [{type: completions}]` ([agentgateway providers](https://agentgateway.dev/docs/standalone/latest/llm/providers/)). It runs standalone from `config.yaml` ([agentgateway](https://github.com/agentgateway/agentgateway)), and v1.6.0 (2026-10-02) added session affinity, per-key local rate limits and graceful draining ([releases](https://github.com/agentgateway/agentgateway/releases)) **[S]**. Azure APIM's self-hosted gateway supports `llm-token-limit` and `llm-emit-token-metric` and lists "self-hosted models and endpoints" as a backend type ([APIM capabilities](https://learn.microsoft.com/en-us/azure/api-management/genai-gateway-capabilities)) **[S]**. Bifrost (`base_provider_type: "openai"` with `allow_private_network`), TensorZero and LiteLLM can all register KVStream as an OpenAI-compatible provider ([Bifrost config](https://docs.getbifrost.ai/quickstart/gateway/provider-configuration); [TensorZero](https://github.com/tensorzero/tensorzero)) **[S]**.

```
Agent framework ──(tools)──► MCP gateway (Docker MCP / ContextForge / agentgateway) ──► tool servers
      │
      └─(completions)─► [optional north gateway: agentgateway | APIM self-hosted | Bifrost | TensorZero | LiteLLM]
                              auth, keys, quotas, guardrails, OTel, (their own cloud fallback if the user wants it)
                                   │  custom OpenAI-compatible provider → http://127.0.0.1:<kvstream>
                                   ▼
                         KVStream  (session-aware admission, KV-token budget, predictive shed + Retry-After,
                                   exact cache, coalescing, breaker, readiness, memory watchdog)
                                   │  dynamic port via /openai/status
                                   ▼
                         Foundry Local (CLI service or SDK 2.x in-process REST, CPU/GPU/NPU EP)
```

**The 503 + Retry-After contract is the most important integration detail.** It behaves differently in each upstream **[S]**:

| Upstream | How it reacts to KVStream's 503 + Retry-After | Source |
|---|---|---|
| Azure APIM | Its circuit breaker sets the trip duration from the backend's `Retry-After`. This is the ideal case. | [APIM capabilities](https://learn.microsoft.com/en-us/azure/api-management/genai-gateway-capabilities) |
| LiteLLM | Cools a deployment after `allowed_fails` (default 3/min) for `cooldown_time` (default 5 s), independent of Retry-After. | [LiteLLM routing](https://docs.litellm.ai/docs/routing) |
| Portkey | Counts `>500` as failures by default, with a 30 s minimum cooldown. One shed burst can take KVStream out of rotation longer than Retry-After asked. | [Portkey breaker](https://portkey.ai/docs/product/ai-gateway/circuit-breaker) |
| agentgateway | Outlier detection evicts throttled or unhealthy backends. Whether it honours Retry-After is unverified. | [Solo failover](https://docs.solo.io/agentgateway/latest/llm/failover/) |

KVStream should therefore publish one reference config per upstream with tuned cooldowns, keep 503 for *capacity* shedding (APISIX's default rejection code too ([APISIX](https://apisix.apache.org/docs/apisix/plugins/ai-rate-limiting/))), and reserve 429 for any future per-client quota, mirroring APIM's 429-rate / 403-quota split ([APIM llm-token-limit](https://learn.microsoft.com/en-us/azure/api-management/llm-token-limit-policy)) **[I]**. Retries must live at one layer: either the agent SDK or the north gateway, never both, and never KVStream ([AWS](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)) **[S/I]**. If a user configures cloud fallback in their north gateway, that is their gateway's feature. KVStream's only obligation is honest health and shed signals **[I]**.

**MCP stays upstream.** MCP gateways federate tool servers, manage `session_id` affinity and filter tools per identity ([agentgateway review](https://dev.to/spacewander/agentgateway-review-a-feature-rich-new-ai-gateway-53lm); [Docker MCP Gateway docs](https://docs.docker.com/ai/mcp-catalog-and-toolkit/mcp-gateway/)). That is a different layer from the completion endpoint **[S]**. The only idea worth borrowing is the session identifier itself. KVStream's `X-KVStream-Session` can be populated by the north gateway from the same agent-run or MCP session ID **[I]**. One caveat applies on a "basic machine": a second proxy process adds a hop and memory. No source measured agentgateway's laptop footprint (Olla's <50 MB is the only local-proxy footprint figure found ([Olla](https://github.com/thushan/olla))). The north gateway should stay optional and documented, not required **[S/I]**.

### What not to build

Per the Foundry-only scope and the evidence, KVStream should not build any of the following **[I]**:

| Do not build | Reason |
|---|---|
| Multi-provider routing, provider failover, virtual models | Mature everywhere upstream |
| Kubernetes/fleet features: InferencePool endpoints, EPP integration, Redis-shared counters | Out of scope for one machine |
| MCP or A2A proxying | MCP gateways and agentgateway already cover tool federation |
| Auth, RBAC and multi-tenancy beyond loopback binding plus an optional static bearer token | Delegate to the north gateway |
| Guardrails, PII redaction and content safety | Delegate to the north gateway |
| Dollar-cost billing | Local tokens are free |
| Semantic caching | Vendors themselves warn it "can surface responses that are incorrect, outdated, or unsafe" ([APIM semantic cache](https://learn.microsoft.com/en-us/azure/api-management/azure-openai-semantic-cache-lookup-policy)). Kong's default embeds only the last message ([Kong reference](https://developer.konghq.com/plugins/ai-semantic-cache/reference/)), which is unsafe for tool-calling traffic. An embedding model would also compete with the main model on the same CPU/GPU/NPU. |
| Model routing à la vLLM Semantic Router | One model, one box |
| Engine-level preemption or KV pinning | Impossible through a black-box Foundry |
| Envoy-style periodic minRTT probe windows | They cause 503s by design |
| LIFO queueing | It conflicts with session continuity |
| Generic llama.cpp/Ollama engine adapters | Scoped out for now, though the notes show they would be easy |
| A Rust rewrite of the data plane | Backend tokens/s, not proxy overhead, is the bottleneck on one machine. Publish the benchmark instead (rank 16). |

## 2026 moved the ground under both the ecosystem and Foundry itself

**Foundry Local is the biggest risk and opportunity.** It "ships as a single native library inside your application", and its SDK "can start an optional OpenAI-compatible REST endpoint within your application process" ([architecture](https://learn.microsoft.com/en-us/azure/foundry-local/concepts/foundry-local-architecture)). SDK v2.0.1 (2026-09-01) unified the Session API and deprecated the OpenAI-style in-process clients. v2.1.0 (2026-09-30) ships ORT GenAI 0.17.1 ([releases](https://api.github.com/repos/microsoft/Foundry-Local/releases?per_page=15)). The CLI REST surface KVStream uses is still flagged as preview, with breaking changes "without notice" ([REST reference](https://learn.microsoft.com/en-us/azure/foundry-local/reference/reference-rest)) **[S]**. Separately, ORT GenAI 0.16 (2026-09-22) added a continuous-batching engine with chunked prefill, paged attention, multi-turn KV retention and smarter token scheduling, and 0.17 auto-enables prefix caching ([onnxruntime-genai releases](https://api.github.com/repos/microsoft/onnxruntime-genai/releases?per_page=12)) **[S]**. There is no evidence that Foundry's REST server uses it yet. If it does, KVStream's "concurrency ≈ 1" calibration becomes wrong, and session-aware ordering gains a second payoff: warm prefix KV for a returning agent. That makes adaptive limits (rank 8) and re-calibration on version change essential, not optional **[I]**. Open issues corroborate the need for a watchdog: unload retaining 98–99% of memory ([#1079](https://github.com/microsoft/foundry-local/issues/1079)), memory growth over time ([#861](https://github.com/microsoft/foundry-local/issues/861)), a vision VRAM leak ending in a crash ([#1034](https://github.com/microsoft/foundry-local/issues/1034)), an NPU model load killing the server ([#829](https://github.com/microsoft/foundry-local/issues/829)), and a tokenizer-lifetime crash under concurrent requests and unloads ([#1091](https://github.com/microsoft/foundry-local/issues/1091)) **[S]**. The last of these argues for KVStream continuing to serialise dispatch to Foundry until concurrency is proven safe on the installed version **[I]**.

**Ecosystem changes** affect which partners to document. Envoy AI Gateway was **renamed Agent Router** and joined the Agentic AI Foundation in September 2026. Its code, CRDs and API group are unchanged, and the docs moved to theagentrouter.ai ([AAIF blog](https://aaif.io/blog/agent-router-powerful-traffic-handling-for-agent-builders)). **agentgateway also joined AAIF** ([AAIF v1.3.0](https://aaif.io/blog/agentgateway-v1-3-0-llm-consumption-reimagined)). **Helicone** was acquired by Mintlify on 2026-03-03 and is in maintenance mode ([Dealroom](https://ai-startups.dealroom.co/news/feed/mintlify-acquires-open-source-ai-observability-platform-helicone)). **LiteLLM** PyPI versions 1.82.7/1.82.8 shipped a credential stealer on 2026-03-24 after a CI compromise ([bastion.tech](https://bastion.tech/blog/litellm-pypi-supply-chain-attack)). **Portkey** was acquired by Palo Alto Networks, announced 2026-06-02; sources disagree on the closing date ([incyber](https://incyber.org/en/article/palo-alto-networks-announced-on-june-2-2026-the-acquisition-of-portkey-a-u-s-start-up-specializing-in-the-control-of-autonomous-ai-agents/)) **[S]**. The implications **[I]**: agentgateway (AAIF, monthly releases) and APIM self-hosted (Microsoft-aligned) are the primary reference topologies. Bifrost and TensorZero (Apache-2.0, independent) are the safest application-layer partners. Helicone should not be a new dependency. KVStream should adopt LiteLLM's lesson on its own release pipeline: pinned dependencies, trusted publishing and no long-lived PyPI tokens in CI.

### Gaps and uncertainties

**Datacenter inference routers.** The planned strand on the Gateway API Inference Extension's flow control, llm-d, Dynamo, SGLang router and LMCache was interrupted and produced no notes. This report covers only the Inference Extension's endpoint picker, criticality classes and shedding, as described above. Any lessons from those systems (e.g. flow-control fairness across criticality bands) remain unresearched.

**Foundry internals.** It is unverified whether Foundry's REST server (CLI or SDK 2.x) uses the ORT GenAI engine, retains prefix KV across requests, or exposes the token-count endpoint in the in-process REST mode. The token-count call's latency, and whether it contends with generation on a serialising runtime, are also unmeasured.

**Program-level scheduling at a proxy.** No published evaluation exists against a single serialising backend, so KVStream's gains must come from its own trace replay.

**Integration behaviour.** agentgateway's laptop footprint, whether its outlier detection honours Retry-After, and Olla's exact breaker and queue semantics were not verified. Absence-of-evidence claims (no idempotency keys, no stream coalescing, no adaptive concurrency elsewhere) rest on docs and READMEs, not source code.

**Third-party figures.** Vendor performance figures (Bifrost µs, LiteLLM sub-ms, TensorZero p99) are unverified self-reports, and third-party LiteLLM criticism traced back to vendor-adjacent posts. Token-normalised adaptive concurrency has no primary-source precedent and is this report's own proposal.

## Conclusion

The survey reframes KVStream's identity. It is not a small LLM gateway competing with LiteLLM or agentgateway. It is the **capacity and continuity layer for one Foundry Local process**: the component that knows how much the box can take, which agent should go next, and when the runtime is quietly dying. The industry's gateways are all built for quota enforcement against elastic remote APIs. That leaves the single-machine overload problem unclaimed, and session-aware admission ("finish admitted agents first") is a capability none of them can offer, because none of them sees a finite backend.

The sharper insight is that KVStream's competitive risk is internal, not external. Its three defects sat exactly in the features that differentiate it (they have since been fixed; see the status note), and Foundry's own trajectory (in-process SDK, possible continuous batching, open memory bugs) can invalidate a hard-coded calibration overnight. A KVStream that tells the truth under failure, re-measures itself when Foundry changes, and slots behind agentgateway or APIM with a documented 503 + Retry-After contract is a stronger product than one with any number of added provider integrations.
